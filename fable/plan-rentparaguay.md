Written 2026-09-09 from `docs/prompts/rentparaguay-vertical.md`,
`docs/rentparaguay-extraction/` and the code at `2c6b6de`. Executed by Opus
and Sonnet sessions; Fable is never an executor of any phase here.

**Why a separate file and not a section of `fable/plan.md`.** That plan is
closed — every phase in it is merged and its §9 says "last phase". This is a
new build with its own decisions, its own §9 log and its own hand-off chain,

re-used by reference below rather than copied; where this file adds a rule it
says so. `CLAUDE.md` beats both files on conventions.

## §1 Decisions already made — do not re-litigate

Repo rules (unchanged — `fable/plan.md` §1 items 1–11 apply verbatim). Plus
the decisions this plan resolves from the code:

1. **Two entries, two keys, one family.** `rentparaguay.com` gets its own
   `VerticalKey` `"rent"`; `alquiler.com.py` keeps `"alquiler"`. Same-key-
   different-locale is not possible in this codebase: the middleware carries
   only the key in `x-vertical`, `currentVertical()` resolves it by first
   match, and `verify:seo` refuses duplicate keys. The `realestateinparaguay.com`
   precedent is exactly this — `en` is a separate key from `inmobiliaria`,
   paired by locale, not by key. What makes the two rental doors one site is a
   **new `family` field** on `VerticalConfig` (item 2), not a shared key.
2. **`VerticalConfig.family: "marketplace" | "rental" | "directory"`.**
   `inmobiliaria`, `en`, `terreno` → `marketplace`; `alquiler`, `rent` →
   `rental`; `agents`, `devs` → `directory`. It exists because `alternates.ts`
   pairs *every served door* as a language version of the same content: with
   the rental doors enabled, `languageAlternates({ path: "/" })` on
   rentparaguay.com would declare `inmobiliaria.com.py/` as its Spanish
   version and `/servicios/...` would be declared as existing on doors that
   404 it. hreflang, the sitemap's static list and the chrome variant all key
   off `family`; per-key overrides (theme, card variant) stay per key.
3. **Both rental doors are `enabled: true` from O1**, overriding the brief's
   "`enabled: false` until reviewed". `resolveVertical()` ignores a disabled
   host, so a disabled door cannot be previewed with a `Host` header and
   `verify:seo` would only ever see a synthetic copy of it. Nothing reaches a
   visitor until each domain's DNS points at Hostinger — that is the go-live
   switch and it is a §7 human step, not a flag. The one thing that must ship
   in the same PR as the flag is the family-scoped hreflang (item 2), for the
   same reason D6 shipped hreflang with the locale flip.
4. **Both rental doors filter `operation: ["alquiler", "alquiler_temporal"]`**
   (the existing `alquiler` entry says `["alquiler"]`). The old site's own
   service list sells short-term "landing" rentals; dropping the door's own
   inventory would be a narrowing the audience never asked for.
   `verticalConds()` already handles a two-member list with `inArray`.
5. **`ownsListingDetail: false` on both**, and `/propiedad` on a non-owning
   door canonicalises to **the served door that owns detail in its own
   locale** — `rent` → `realestateinparaguay.com`, `alquiler` (and `terreno`)
   → `inmobiliaria.com.py`, primary as the fallback. `verify:seo` forbids two
   served doors owning detail in one language, and `en`/`inmobiliaria` already
   own English and Spanish. Today every non-owner canonicalises to the Spanish
   primary; an English page whose canonical is a Spanish URL is a canonical
   Google ignores. The detail page does not filter by vertical
   (`getListingByPublicId` selects by `public_id` only), so the target always
   renders. Sitemap: non-owners omit `/propiedad` as they do now.
6. **The lead form uses the existing pipeline only. No Resend.** There is no
   Resend anywhere in the codebase (grep is empty); `src/lib/crm.ts` is by
   contract "the ONLY file that knows which provider delivers messages", and
   the lead row in MySQL is the record. `/api/leads` already stamps
   `leads.vertical` from `x-vertical` (its column comment literally names
   `'alquiler'`), routes a listing-less lead to `internal`, shows it in
   `/admin/leads`, and pushes a copy to `LEAD_WEBHOOK_URL` after the response.
   An email to the founder is a webhook target (n8n/GHL → mail), zero code.
   Sending mail inside a request is the 503 shape PLAN.md documents, and
   `hello@rentparaguay.com` is not a real mailbox — CLAUDE.md's "no
   placeholder address" rule holds on these doors too.
7. **Lead type mapping, no enum change.** `lead_type` stays the existing enum.
   Rent apartment/house, residency, virtual address → `renter`; Airbnb
   management, apartment management → `seller` (the "I own a property" lane);
   invest, realtor → `buyer`; the `/contacto` reason selector offers these
   three, labelled in the door's language. The service name travels as
   `utm.source = "rental:<service-slug>"` (the `VenderForm` precedent,
   `source: "vender"`) and as the first line of `message`, so `/admin/leads`
   can tell them apart without a column.
8. **URLs use Spanish slugs on both doors** (`/servicios/...`, `/nosotros`,
   `/contacto`, `/alquiler`), the app-wide rule `alternates.ts` documents
   ("every URL in this app is built from Spanish slugs"). The old English
   paths 301 to them, host-scoped to `rentparaguay.com` (Appendix A).
   `pathByLocale` stays unused; localising slugs later is that hook, not a
   route change.
9. **Brands:** `alquiler.com.py` → "Alquiler Paraguay", `rentparaguay.com` →
   "Rent Paraguay". The domain is the brand (CLAUDE.md); the existing
   "Alquiler.com.py" string is replaced to match "Inmobiliaria Paraguay" /
   "Real Estate in Paraguay". No wordmark image: the header renders the brand
   string and the line icon like every other door; the extracted logo PNGs
   are palette reference only and are not shipped.
10. **One theme for the family.** A `RENTAL` token set in `themes.ts`,
    assigned to both `alquiler` and `rent` — the two doors are one business in
    two languages, unlike the marketplace pair, which are two brands. Type and
    shape reuse Nórdico's (Manrope is already installed, 10px radius, one soft
    shadow); only the palette is new, derived from the extracted logo files,
    contrast computed and written down like `OVERRIDES.en`.
11. **Chrome:** no login, no publish CTA, no newsletter on either rental door
    (`chromeShowLogin` / `chromeShowPublishCta` / `chromeShowNewsletter` return
    `false` for the `rental` family). The header CTA is "Contactanos" /
    "Contact us" → `/contacto`. Nav: Alquileres (`/alquiler`) · Servicios
    (`/servicios`) · Nosotros · Contacto, labels from the `rental` namespace.
12. **Cards and figures:** `cardVariant` → `framed-pill` for both rental keys;
    `secondaryAreaUnit` → `sqft` for `rent` only; `showCuota` → `false` for the
    rental family (a cuota is a purchase figure; none renders on a rental card
    anyway — the flag makes the intent explicit).
13. **Fabricated content is dropped, not translated**: the Brickon demo
    listings, the three "team" members and their photos, every testimonial,
    the "400+ agents … altora" line, the zero-state counters. The founder bio
    is the only person on `/nosotros`. Where the old site's copy claims a
    measured figure ("within 48 hours", "approved on the first attempt") the
    new copy states the service, not the number — the same rule
    `esNordico.proofRow`'s comment already applies.
14. **Gating:** `/servicios`, `/servicios/[slug]` and the rental branches of
    `/`, `/nosotros`, `/contacto` render only for the `rental` family; other
    doors `redirect("/")` from `/servicios*` exactly as `/vender` does off the
    Spanish door. Marketplace-only pages keep rendering on rental doors (the
    `terreno` precedent) but no rental chrome or copy links to them, and the
    rental sitemap does not list them.
15. **Model guardrail** (`fable/plan.md` §4.8): Opus and Sonnet only. Fable
    wrote this file and never runs a phase.

## §2 Object model — what the build adds

  filters doors to the current family; x-default is the family's Spanish
  door, primary when it is in the family), `sitemap.ts` (static list per
  family), `sections.ts` (`chromeVariant`, `homeLayout`, `rentalPagesEnabled`),
  `origin.ts` (item 5).

  key, `leadType`, hero image path, old URL. The services hub, the detail
  route, the redirect map, the sitemap and the footer all read this one list.
- i18n namespaces `rental` (chrome, home, about, contact, services hub, the
  shared service-page furniture) and `rentalServices` (one object per
  service, fixed shape — Appendix C), `es.ts` + `en.ts` in the same commit,
  assembled in `index.ts`, walked by `verify:i18n`. `leadForm` namespace for
  `LeadForm`'s literals (Spanish byte-identical).
- Components: `src/components/home/RentalHome.tsx`, `RentalAbout.tsx`,
  `RentalContact.tsx`, `RentalServicesHub.tsx`, `RentalServicePage.tsx`. Fork
  points: `app/page.tsx` (already the allowed one), `app/nosotros/page.tsx`
  and `app/contacto/page.tsx` gain the same one-line registry fork.
- Routes: `app/servicios/page.tsx`, `app/servicios/[slug]/page.tsx`.
- Static assets: `public/img/rental/*.webp` (Appendix B). Ordinary static
  files, not the R2 listing-photo pipeline.

## §4 Autonomy protocol

`fable/plan.md` §4 applies in full (work to exit criteria; one PR per phase
off a freshly reset `origin/main`; minor issues → `fable/KNOWN-ISSUES.md`;
stop only for a missing credential or a foundation decision; re-runnable
prompts; Sonnet hard limits; no Fable; four hand-off gates; §9 entry before
merge). Three additions for this plan:

- **§4.11 Family-scoped SEO is a check.** Any phase that touches
  `verticals.ts`, `alternates.ts`, `origin.ts`, `sitemap.ts` or
  `site-nav.ts` runs `npm run verify:seo` and `npm run verify:facets` and
  says so in the PR. O1 extends `verify:seo` with the rental-family spec
  (§5.1); later phases must keep it green, never edit it to pass.
- **§4.12 Preview by Host header.** "Rendered on the rental doors" means
  `npm run build && npm run start` and `curl -H "Host: rentparaguay.com"` /
  `-H "Host: alquiler.com.py"` against the page (or the same header in a
  browser via `next dev`). A page that only looks right on `localhost`
  looks right on `inmobiliaria.com.py`.
- **§4.13 Sonnet fan-out.** Same-shaped units (the seven service pages) are
  built as template + one exemplar first, then the rest as parallel Sonnet
  subagents per the `fable-directs-sonnet-builds` skill; one verify, one PR.
  Subagents are Sonnet, never Opus or Fable.
- **§4.14 Hand-off between the two sessions.** The Opus session ends after
  O3 is merged with a report; it spawns the Sonnet session (`create_session`,
  `model` explicitly Sonnet, prompt `Read fable/prompts/sonnet-1-rental-assets.md
  in this repo and execute it.`) only if O1–O3 are all on `origin/main`.
  Inside each session, the next phase starts in the same window (same model).
