# Security and performance audit — 2026-10-02 (O10)

Branch `claude/audit-2026-10`. Spec: `docs/plan-admin-next-2026-10-02.md`, item
O10. This file was committed first; the fixes follow in later commits.
Auth fixes are in a separate PR that an agent never merges.

## Scope and method

Four read-only sweeps ran in parallel, then I re-read every finding marked
high or medium in the code before deciding what to do with it:

1. **Server actions.** 32 `"use server"` files, 97 exported actions. For each:
   - which guard it calls, and whether before any read or write;
   - whether the write is scoped to what the user may touch (IDOR);
   - whether staff can reach super-admin work;
   - input bounds;
   - whether anonymous actions are rate-limited.
2. **Raw SQL.** All 16 `sql.raw(` sites, every interpolated `sql` template,
   mysql2 `query()` calls, LIKE patterns, ORDER BY and LIMIT taken from input,
   and JSON paths.
3. **Auth and session.** Sessions, guards, login, logout, registration, reset,
   invites, OTP, Telegram linking, role changes, cookie flags, CSRF on route
   handlers, open redirects, and the headers the middleware trusts. Builds on
   `docs/log/security-review-2026-10-01.md`, which covered `/api/*`. No
   `route.ts` was added since then; the two changed ones (`/api/leads`, the
   leads CSV) were re-checked.
4. **Performance** of /admin, /agencia and /mis-avisos:
   - N+1 queries and unbounded reads;
   - every hot predicate against the indexes declared in `schema.ts`;
   - round trips and fan-out against the 6 + 24 pool.

Nothing ran against production. No EXPLAIN against real data: index claims come
from comparing the queries with `schema.ts`.

## Server actions

Every guarded action calls its guard on its first line, before any read or
write. These are kept off staff:

- delete lead
- deals and money
- delete or publish a listing
- settings
- users
- import
- operations
- partner invites

The public actions are:

- `estimateAction` and `requestValuationContactAction` (/tasacion), covered by
  S1 and S2;
- `confirmAlertAction` and `unsubscribeAlertAction`: the token is the
  credential;
- `requestResetAction` and `resetPasswordAction`: rate-limited, with an HMAC
  token;
- `registerAction`: 5 per IP per 10 minutes;
- `loginAction`: covered by A1.

**S1 — `app/tasacion/actions.ts` `requestValuationContactAction`.**
- **The problem:** the only anonymous lead writer that skips
  `allowRequest`. A loop of calls inserts `valuation` leads, pings the
  operator's Telegram and email, and pushes to VenderCRM each time.
  `canonPhone()` output was length-checked from below only (`leads.whatsapp` is
  varchar(30)), and a non-string field threw a 500.
- **The fix:** the same per-IP bound as `/api/leads` (10 per 10 minutes),
  6–15 digits, and type checks on every field.

**S2 — `estimateAction`.**
- **The problem:** wrapped in `unstable_cache` keyed by its arguments. A
  unique float area or a random slug per call is a guaranteed miss: three
  queries against the pool, plus one more cache entry.
- **The fix:** the slug must look like a slug, the area is rounded to whole
  m² and bounded (1–1 000 000), and there is a generous per-IP bound (60 per
  10 minutes). A real visitor adjusting the form never reaches it.

**S3 — `src/lib/listing-form-input.ts`, and the /publicar draft.** The price
must be below `DECIMAL(14,2)`'s 1e12, and the description is cut to the
`text` column's 65 535 bytes, counted conservatively as 16 000 characters.

**S4 — `saveDraftAction`.** 60 saves per user per 10 minutes. The wizard saves
once per step, so a person is nowhere near it.

## SQL (all 16 `sql.raw` sites)

All of them spell a constant, a validated integer or an enum member:

- `publisher-kind.ts`: the `partner_agent_ids` and `house_agency_id` settings,
  parsed twice;
- `contact-kind.ts`;
- the triage filters in `panel-queries.ts` and `listing-edit.ts`;
- the analytics dimensions;
- the job intervals.

LIKE input always goes through `src/lib/sql-like.ts`. ORDER BY is chosen from a
whitelist. LIMIT and OFFSET are bound, and `?page` is capped. The mysql2
`query()` calls are static.

Hardened here, so the safety sits next to the raw call instead of in another
file:

- **Q1** `contact-kind.ts`: an assertion that the utm key is a plain
  identifier before it is quoted into a JSON path.
- **Q2** `analytics-queries.ts` `topDimension()`: the column comes from a
  const map, and anything else throws. Today it is safe only through its type.
- **Q3** `panel-queries.ts` and `listing-edit.ts` triage filters: the literal
  is spelled from the enum's own element, not the request value.
- **Q4** `publisher-kind.ts`: the house agency id uses `isSafeInteger`, like
  the partner ids.
- **Q5** `countRecentLeads(hours)`: a non-finite argument falls back to 24.

## Auth and session (separate PR, never merged by an agent)

Checked and sound:

- **Sessions:** 32-byte random tokens, stored as sha256. The role is re-read
  on every request, so a demotion or deletion bites at once.
- **Password changes** purge every session on every path.
- **Cookie:** `httpOnly`, `Lax`, `Secure` in production, per host.
- **Login:** a dummy scrypt hash keeps timing equal, and `safeNext` blocks
  open redirects.
- **Reset:** HMAC over the current hash, constant-time comparison, links only
  to hosts the app serves.
- **Invites:** the agency and role come from the database row, claimed in one
  guarded UPDATE.
- **Last-admin guards** are in place.
- **Telegram linking** never overwrites a linked chat.
- **Headers:** the middleware overwrites `x-vertical`, `x-locale` and
  `x-nonce`; proxy trust is checked in constant time.
- **Route handlers that read the session** are GET-only with the page's own
  predicate, so there is no CSRF surface.

A1–A6 are in the auth PR. D1, D2 and D4 are founder decisions, written into
`docs/decisions-needed.md`.

## Performance

No per-card N+1 was found. The page loaders batch with `IN (…)` on indexed
columns: shares, deals, matches, threads, WhatsApp and attachments.

- **P1** — `getPanelListingStats(scope, internalOnly, onlyListingId)`
  (`src/lib/stats-queries.ts`) narrows the scoped id read to the one listing,
  still through the scope's WHERE. The three aggregates then run on
  `IN (that id)`, served by the primary key of `listing_views_daily` and by
  `idx_listing` on `leads` and `analytics_events`. The three edit pages pass
  the id.
- **P2** — `getPanelLeads()` takes a limit: 300 on the pages, the same as
  `getSharedLeads()`. The CSV exports keep reading everything.
- **P3** — `JoinedListingsNotice` uses one `IN` query for all events.
- **P4** — `/admin/calidad` selects the description's length, not its text.
- **P5** — `listAgentMatchCandidates` filters `agent_id IS NOT NULL` in SQL.
- **P6** — `cachedHealth` is wrapped in `singleFlight()`.
- **P7, fixed in part.** The three rounds that depend only on the page's rows
  (deals, WhatsApp, D3 matching) now run as one round of at most six reads.
  - Still open: fold the six chip counts into one grouped pass
    (`lead_type, vertical, status, contact kind, publisher kind, is_report`).
  - Why it waits: it touches every chip on the busiest admin page, so it gets
    its own change with a seeded before/after comparison.
- **P8, still open** — read complete days from `analytics_daily` and only
  today from raw events. Per-dimension unique visitors in the rollup are an
  upper bound, so the numbers on the page would change meaning. That needs a
  decision on what the page promises, or a short `unstable_cache` instead.
- **P9** — the four indexes are proposed in the migration of the O2/O8 PR
  (`MIGRATION REQUIRED —`). It is one migration for the founder to run, and
  the indexes are pure additions.
