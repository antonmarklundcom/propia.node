# T1 — terreno.com.py agency/agent rail leak

`getAgencyListings()` / `getAgentListings()` (`src/lib/queries.ts`) filtered
only on `status` + `agencyId`/`agentId`, so the "Más de esta
inmobiliaria/este agente" rail on `/propiedad/[slug]` and the grids on
`/inmobiliaria/[slug]` and `/agente/[slug]` ignored a door's `filters`
(`terreno.com.py`'s houses/flats leaked into a terreno rail).

Fix: added an optional `vertical?: VerticalConfig` param to both, spreading
`...(params.vertical ? verticalConds(params.vertical) : [])` into `conds`,
matching `getRecentListings`. Passed `vertical` from all three callers —
already awaited via `currentVertical()` on the detail page; added it to both
profile pages.

Not touched: `countAgencyListings`/`countAgentListings` (indexability) —
still unfiltered by vertical, per plan §10 backlog (decide whether a
profile with only non-terreno listings should be indexable on
terreno.com.py).

No cache-key change needed: neither function is `unstable_cache`d.

No local DB in this environment — verified via `npm run verify:local`
(typecheck, build, verify:import, verify:facets, verify:i18n, verify:seo,
all pass) and by reading the resulting WHERE clause: on `terreno.com.py`
`verticalConds()` adds `property_type IN ('terreno')`, so a mixed-inventory
agency's casa rows are excluded from both queries; on `inmobiliaria.com.py`
(no `filters`) `verticalConds()` returns `[]`, so behavior is unchanged.
