## What landed

- **Schema** — `email_messages` (mailbox, direction, from/reply-to/to/cc,
  subject, text, sanitized HTML, Message-ID, In-Reply-To, References,
  `thread_key`, `lead_id`, `dedup_key` unique, `sent_by_user_id`,
  `send_error`, `read_at`, `archived_at`) and `email_attachments` (R2 key,
  filename, content type, size). Addresses are comma-separated text, not
  `json` (MariaDB hands `json` back as a string).
- **`workers/inbound-email/`** — Cloudflare Email Worker (postal-mime,
  wrangler). Signs `<timestamp>.<body>` with HMAC-SHA256; forwards the
  original to `FALLBACK_FORWARD` on any non-2xx, timeout, missing secret, or
  when an attachment was over the inline cap (5 MB each, 9 MB total).
  Optional `COPY_TO` keeps the Gmail copy during the transition. README has
  the deploy steps.
- **`/api/inbound-email`** — 503 without `INBOUND_EMAIL_SECRET`; 16 MB cap
  read incrementally; constant-time signature check, ±5 min; zod payload;
  idempotent on mailbox + Message-ID; attachments to R2 (private bucket or
  random `inbox/` keys) before the row is written, metadata only when R2 is
  off; `alertOperator()` (`kind: "new_email"`) in `after()`, never for a
  duplicate, our own `mail.` machine mail or `Auto-Submitted` mail.
- **Threading** (`resolveThread()` in `src/lib/inbox.ts`): signed
  `lead-<id>-<sig>@` recipient → that lead; else In-Reply-To/References
  match → that thread (and its lead); else same mailbox + counterpart +
  subject without Re: within 60 days; else a new thread.
- **E2** — the seeker confirmation carries Reply-To `lead-<id>-<sig>@mail.…`
  (only while inbound is configured) and is recorded as the thread's first
  message. The thread shows under the lead card in `/admin/leads`,
  `/agencia/leads` (own + shared) and `/mis-avisos/consultas`, with a reply
  box and "Marcar como leído". Replies go through `sendEmail()` with
  In-Reply-To/References, from `EMAIL_FROM` under the lead's door brand,
  signed with the panel user's name.
- **E3** — `/admin/inbox`: Bandeja / Archivados / Respuestas a consultas,
  Redactar, thread page (reply, archive, "Convertir en consulta"), unread
  badge on the Correo tab (on `/admin` and the inbox pages). Staff see
  hola@/contacto@ only.
- **`email.ts`** — `cc`, threading `headers`, and `fromMailbox`: sent *as*
  a root mailbox only with `EMAIL_ROOT_SENDING=true`, else from `EMAIL_FROM`
  with that mailbox as Reply-To (`senderFor()`). Still the only sender.
- **`r2.ts`** — `putPrivateObject` / `getPrivateObject` /
  `deletePrivateObjects` (`R2_INBOX_BUCKET` or the photo bucket).
- **Visibility** — `getPanelLeads(scope, leadId?)`,
  `isLeadSharedWithPanel()`, `panelCanSeeLead()`, `userMaySeeLead()`: the
  existing predicates asked for one id. `verify:scopes` gained 18 checks.
- **`db:status`** — fixed for MySQL 8 (information_schema returns
  upper-case column names there; aliased). MariaDB was unaffected.
- **i18n** — `es-e2.ts` / `en-e2.ts` (`inbox` in the dictionary).
- **`npm run verify:inbox`** — pure: signature (node:crypto vs WebCrypto),
  lead addresses, sanitizer, sender rule, header injection. In `verify:local`
  and `.githooks/pre-push`.

## Verified in the sandbox

- `npm run verify:local` green; `npm run verify:scopes` green against a local
  MySQL 8.4 (docker compose); `db:status` → migrate → `db:status` (No drift).
- End to end against `next start` + local MySQL, with only the Cloudflare
  Email Sending and Telegram HTTP endpoints faked (a `--require` preload that
  logs what would be sent). The real Worker module was driven from Node with
  fake Email Routing messages: stored, duplicate, In-Reply-To threading,
  signed lead address, guessed lead address, wrong secret → forward, app down
  → forward, 6 MB attachment → metadata + forward, auto-reply → no alert,
  anton@, no secret → forward, no fallback → bounce.
- Playwright (Chromium): admin inbox list/thread/remote-image toggle/reply
  headers/compose/archive/convert/lead reply; staff cannot see anton@ (404 by
  URL) or an owner-lane lead's thread; owner sees and answers their lead's
  thread; no horizontal scroll at 390 px.
- `wrangler deploy --dry-run` bundles the Worker (113 KiB); `tsc` clean.

## Not verified (no real Cloudflare from the sandbox)

- A real Email Routing → Worker delivery, `message.forward()` and
  `setReject()` on Cloudflare; the subdomain catch-all on `mail.` next to
  Email Sending's records.
- A real Cloudflare Email Sending call with `headers`/`cc` (the request body
  shape is checked against Cloudflare's docs and by `verify:inbox`).
- R2 uploads/downloads of attachments (no R2 credentials here; the
  metadata-only path is what ran).
- Hostinger's proxy body-size limit for `/api/inbound-email`: if it is under
  the Worker's ~12 MB worst case, a big message gets a 413 and goes to
  `FALLBACK_FORWARD` — safe, but check `wrangler tail` once.
